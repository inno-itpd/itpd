# Assignment 8 Design Decisions

This file records the key decisions behind Assignment 8 and the requirements it depends on, and the reason for each.
It is maintainer documentation for the course materials, not part of them: students follow the assignment and the requirements, and this file explains why those read the way they do.
The entries are `A8-DEC-nnn`, zero-padded and never renumbered or reused, in design order, from the week's scope to the order its parts are worked in.
A revision an entry received while the assignment was being written is folded into it, so each entry states the design as it now stands; a later reversal gets a new entry whose `**Reverses:**` names the one it replaces, as a `DEC-nn` is reversed per [Reversing A Decision](../../requirements/decisions-requirements.md#reversing-a-decision).
An entry that reverses an `A7-DEC` records the whole reversal and restates the clauses that survive, because a reversal cannot be partial.
Mechanical edits — backlog housekeeping and the dates a decision here sets — are not design decisions and are not recorded here.

## A8-DEC-001: Week 8 Runs The Test And Reviews The Configuration

- **Status:** Accepted
- **Decision:** the `UT-01` sessions run at the dates the team schedules, from the Week 7 class week to the Week 8 deadline; Week 8 writes the results, writes the findings, triages them, and reviews the configuration.
  The results are Submission 8's main result, and the configuration review is the week's second stream: the configuration plan and its goal-based evaluation.
  The fixes are planned rather than promised, and no fix is forced; the configuration review is full-depth and the implementation is not.
  The evaluation's first change and its other changes are added to the Week 9 backlog.
- **Why:** the design week ends with a test nobody has run, so the run week owes the results; and the configuration was supplied by the course and built over seven weeks, so the week that reviews it judges an existing configuration rather than designing a new one.
  A week that required both an implementation and a test whose participants must be arranged would make the test compete with a change the maintainer does not need.
- **Alternatives considered:** moving the review to Week 9, rejected because the week is the deck and the final repository state and the review's changes would arrive after the freeze; requiring the implementation, rejected because it penalises a team that ran the test in the same week; and running the sessions only after the Week 8 deadline, rejected because the results are due with Submission 8.
- **Where it lands:** [Assignment 8](../../assignments/assignment-8.md), [the syllabus](../syllabus.md#week-8-nov-13--nov-19-project-configuration-management), [The Parts Assignment 8 Carries](../plans/a8-plan.md#the-parts-assignment-8-carries), and [The Week 8 Execution](../../requirements/usability-testing-requirements.md#the-week-8-execution).

## A8-DEC-002: The Review Is Whole-Repository

- **Status:** Accepted
- **Decision:** the review judges the whole repository configuration: the delivery configuration the customer reaches and the context an agent reads, in five groups — source control and release, checks, environments and secrets, dependencies and builds, and agent context and artifacts.
  The criteria are the course's own configuration rules, linked from each item's `**What good looks like:**` rather than restated in a table, and the course materials are an upstream item the team installs and wires in, judges, and does not edit.
  A defect in the product's own behaviour is a risk or a task issue rather than a configuration item.
- **Why:** a review that judges only the product code would miss the configuration an agent actually reads, and a review that judges only the agent context would miss the checks and the delivery that make the product trustworthy; the two are one configuration and one week to judge.
  The course materials are a read-only submodule, so a team that "fixed" them would diverge from the course and lose the next update.
- **Alternatives considered:** judging only the CI and the deployment, rejected because the Week 8 deck teaches configuration management as the trustworthiness of the artifacts an agent reads; adding a sixth group for the product code, rejected because the product is judged by its requirements and its tests rather than by its configuration; and letting the team edit the submodule, rejected because the fixes would be lost on the next move to the latest materials.
- **Where it lands:** [The Configuration Items](../../requirements/configuration-management-requirements.md#the-configuration-items), [Assignment 8 Part 7](../../assignments/assignment-8.md#part-7-write-the-configuration-plan), and [Step 2](../../guides/configuration-management.md#step-2-inventory-the-configuration).

## A8-DEC-003: The Configuration Plan Is Maintained And The Evaluation Is The Week's Evidence

- **Status:** Accepted
- **Decision:** the configuration plan is maintained at `docs/configuration-plan.md`, and the configuration review is the week's evidence at `reports/week-NN/cm-evaluation.md`, which is `reports/week-08/` for the week `UT-01` runs in.
  The plan is in the `docs/` destination map and the routing tables, `README.md` and `course/rules.md` gain the requirements row, and `README.md`, `SKILL.md`, and `course/rules.md` gain the guide row.
  The weekly report example removes the separate improvement-plan and implementation rows, keeps one `Configuration management` row pointing at the section's anchor, and lets that section link the plan and the evaluation, so neither artifact gets a row of its own.
- **Why:** the plan will still be read in Week 9, and the evaluation is a judgement of one state that a later week cites rather than maintains; a single `Configuration management` row keeps the coverage table an index rather than a second list of links.
  A plan under `reports/` would be rewritten by the next week and would describe the configuration at the one moment it was written.
- **Alternatives considered:** keeping both artifacts in `reports/week-08/`, rejected because the plan is read later and the two-location rule puts maintained documentation in `docs/`; keeping the 2025 `docs/configuration-management/self-review.md` shape, rejected because the plan and the judgement have different lifetimes and different readers; and giving the plan and the evaluation a coverage row each, rejected because the report's section already links both.
- **Where it lands:** [Where The Configuration Plan And The Review Live](../../requirements/configuration-management-requirements.md#where-the-configuration-plan-and-the-review-live), [Where Artifacts Live In The Repository](../../requirements/general-requirements.md#where-artifacts-live-in-the-repository), [Weekly Public Report](../../requirements/weekly-report-requirements.md#weekly-public-report), and [the README's guide table](../../README.md#the-guides).

## A8-DEC-004: The 2025 Attribute Grid Is Not Carried

- **Status:** Accepted
- **Decision:** the 2025 configuration-management assignment's rating of each component on `Visibility`, `Accessibility`, `Accountability`, `Traceability`, and `Evolvability` with `Absent`, `Present`, or `Strong` is not carried.
  The plan's fields are the item's metadata, the evaluation judges the local goals the artifacts serve, and no maintenance, token, or failure cost is measured.
  The criteria are linked from each item's `**What good looks like:**` rather than restated in a grid.
- **Why:** the 2026 deck does not teach those attributes, so a team would be graded against five words the lecture never used; and a three-value rating invites a cell filled to look thorough, which is the failure the plan's goal test exists to prevent.
  The attributes also rate an item in itself, while the maintainer's question is whether the set of artifacts is the most convenient way to achieve a goal.
- **Alternatives considered:** keeping the grid beside the new fields, rejected because two judgements of the same item disagree within a week; and measuring the cost of each item, rejected because the numbers would be invented and a sentence a reader can check is worth more than a cell.
- **Where it lands:** [The Evaluation](../../requirements/configuration-management-requirements.md#the-evaluation), [The Configuration Items](../../requirements/configuration-management-requirements.md#the-configuration-items), and [Step 5](../../guides/configuration-management.md#step-5-judge-each-goal).

## A8-DEC-005: The Configuration Plan's Fields

- **Status:** Accepted
- **Decision:** an item carries `**Status:**`, `**Dropped:**`, `**Type:**`, `**Purpose:**`, `**Owner:**`, `**Where:**`, `**Connections:**`, and `**What good looks like:**`, and the document carries `**Reviewed:**`.
  It carries no `**Baseline:**`, no `**Properties:**`, no `**Version:**`, no connections table, and no `## Dropped Items` section.
  The plan carries at least 8 `Active` items in the five groups, with at least one in each, and a dropped item stays in its group with its `**Status:**` and its `**Dropped:**` date and reason.
- **Why:** the repository's history and the evaluation's `**Baseline:**` already identify the state, so a per-item version or a document-level baseline is a second copy of the same fact; and a connections table beside the items is the copy that goes stale, while the item's own field is where a reader following an edge already is.
  A dropped item in place keeps the inventory readable as the repository grows, because the live items are not scattered through a history section.
- **Alternatives considered:** a version per item, rejected because nothing reads it and a version conflicts with the tag that already names the released state; a connections table, rejected because the same edges would then exist twice; and a `## Dropped Items` section, rejected because it separates an item from the group it explains.
- **Where it lands:** [The Configuration Items](../../requirements/configuration-management-requirements.md#the-configuration-items), [The Connections](../../requirements/configuration-management-requirements.md#the-connections), [Assignment 8 Part 7](../../assignments/assignment-8.md#part-7-write-the-configuration-plan), and [Assignment 8's checklist](../../assignments/assignment-8.md#checklist).

## A8-DEC-006: `CFG-nn` Is The Week 8 Family

- **Status:** Accepted
- **Decision:** `CFG-nn` is the Week 8 identifier family: two digits, repository-wide, one section per item at `### CFG-01` in `docs/configuration-plan.md`, with the identifier alone as the heading and the item named on the first line.
  Its status is `Active` or `Dropped`, its other fields and its dropped form are the configuration-management requirements', and the evaluation cites the identifier with the plan's path or heading anchor.
  A configuration the team does not have receives a `CFG-nn` only once it exists.
- **Why:** an item without a stable anchor cannot be cited from a goal section, and the course's identifier rules already make the heading the link target; a family introduced by the requirement that first uses it is how every earlier family arrived.
- **Alternatives considered:** citing an item by its path, rejected because a set of files is one item at an index and a path is not stable across a move; and reusing an existing family, rejected because a configuration item is not an artifact of one of the earlier kinds.
- **Where it lands:** [Identifier Rules](../../requirements/general-requirements.md#identifier-rules), [The Configuration Items](../../requirements/configuration-management-requirements.md#the-configuration-items), and [the course AGENTS conventions](../../AGENTS.md#conventions).

## A8-DEC-007: The Review Is Full-Depth And Goal-First

- **Status:** Accepted
- **Decision:** the review is full-depth: at least 8 `Active` items with at least one in each of the five groups, every item carrying its fields and its connections, and the evaluation carrying one section per local goal.
  The evaluation walks the goals the artifacts serve, not the five groups one by one, and an item no goal section names is still in the plan and is kept unless a goal section proposes a change to it.
  No minimum number of local goals applies, and an item the team could not judge is the `What We Could Not Judge` note with the reason and the risk.
- **Why:** the groups are a way to find the items and the goals are a way to judge them; walking the five groups would produce five audits rather than one judgement of whether the set is right-sized.
  A minimum goal count would make a team invent a goal, and the missing-item list a shallow review produces pushes a team to add configuration the course does not want.
- **Alternatives considered:** a per-item review with each item marked keep or change, rejected because it judges the artifact rather than the goal and produces no tradeoff; and a review of the delivery groups only, rejected because the artifacts an agent reads are half the configuration.
- **Where it lands:** [The Configuration Items](../../requirements/configuration-management-requirements.md#the-configuration-items), [The Evaluation](../../requirements/configuration-management-requirements.md#the-evaluation), and [Assignment 8 Part 8](../../assignments/assignment-8.md#part-8-write-the-goal-based-configuration-evaluation).

## A8-DEC-008: The Public Review Is Sanitized

- **Status:** Accepted
- **Decision:** the configuration plan and the evaluation carry no secret value, no private deployment or dashboard address, and no credential.
  A goal section that names a failing item and its consequence stays public in words, and the value and the step-by-step that would let a reader use the weakness do not appear.
  A settings page is named in words rather than linked, the deployment address stays in the Moodle submission, the review adds no appendix to the wrapper, and a leaked credential follows the incident response.
- **Why:** the product repository is public and permanent, and a review is exactly the document that would name the one address nobody should publish; the sanitized version costs the reader nothing, because the property that fails and its consequence are what the review is for.
  A settings page needs authentication, so a link to one is a dead end in a public file.
- **Alternatives considered:** a private review in the Moodle wrapper, rejected because the review is the week's evidence and the course grades public artifacts; publishing the address with a warning, rejected because a warning is not a control; and adding a configuration appendix to the wrapper, rejected because the deployment addresses it touches are already there.
- **Where it lands:** [The Public Review](../../requirements/configuration-management-requirements.md#the-public-review), [Sensitive Information Reference](../../requirements/visibility-requirements.md#sensitive-information-reference), [Sensitive-Data Incident Response](../../requirements/repository-requirements.md#sensitive-data-incident-response), and [Assignment 8 Part 8](../../assignments/assignment-8.md#part-8-write-the-goal-based-configuration-evaluation).

## A8-DEC-009: The Evaluation Carries The Changes

- **Status:** Accepted
- **Reverses:** [`A7-DEC-022`](a7.md#a7-dec-022-the-week-8-workload), in full: its decision that the Week 8 workload is the analysis, the findings, the triage, the results, and "the CM work", and its Why that Week 8 "already carries the CM evaluation, the improvement plan, and the implementation", do not hold.
  The clauses that survive: the sessions run from the design to the Week 8 deadline, 15 to 18 November is the suggested window, the analysis and the triage follow the sessions, and the `QR/QRT` fallback stands when the test cannot finish.
  The CM work is the configuration review rather than a separate plan and an implementation.
- **Decision:** the evaluation's goal sections and its first change are the recommendation, and no separate improvement plan is required.
  No implementation is required in Week 8, and an optional change is the same work under the existing rules: a task issue, a pull request, the configuration plan updated in the pull request that records the change, the green checks, and the release when the change is product-visible.
  The first change and the other changes are added to the Week 9 backlog, and Week 9 schedules them alongside its other planned items.
  The syllabus's Week 8 deliverable 2 is removed, deliverable 3 is made optional, and the assessment catalog's Submission 8 row becomes "the configuration plan and its goal-based evaluation".
- **Why:** a separate plan beside an evaluation is a second document that says the same thing and goes stale on one side; the goal sections already say what would change and why, and the first change is the one a reader needs.
  The implementation would make a team that ran the test in the same week choose between its results and a change nobody asked it to need.
- **Alternatives considered:** keeping an improvement plan derived from the evaluation, rejected because it duplicates the goal sections and no reader needs both; requiring one enacted change, rejected because it penalises the team that ran the sessions late; and moving the changes entirely to Week 9 without a first change, rejected because the evaluation then ends with no commitment and Week 9 has nothing ordered to schedule.
- **Where it lands:** [The Recommendation](../../requirements/configuration-management-requirements.md#the-recommendation), [The Evaluation](../../requirements/configuration-management-requirements.md#the-evaluation), [the syllabus](../syllabus.md#week-8-nov-13--nov-19-project-configuration-management), [Assignment 8 Part 8](../../assignments/assignment-8.md#part-8-write-the-goal-based-configuration-evaluation), and [Week 9's plan section](../../requirements/planning-requirements.md#full-example).

## A8-DEC-010: The Usability Results Are Assignment 7's Rules

- **Status:** Accepted
- **Decision:** the results, the findings, the triage, the verdict, and the release are the `**Since: W8**` rules Assignment 7's plan already wrote, and Assignment 8 assigns them.
  A significant finding's task issue is scheduled in `SPRINT-08`, a fix that lands is in `REL-08`, a fix that does not land moves to `SPRINT-09` at the sprint close, and the report declares the move.
  A finding is significant when its `**Severity:**` is `Critical` or `Major`, and no fix is forced when the test finds nothing significant.
- **Why:** the rules were designed with the test they grade, so a second statement of them would be the copy that goes stale; the one thing the run week needs that the design week did not is the word "significant", which is a defect in the rule rather than a new rule.
- **Alternatives considered:** writing the week's usability rules in Assignment 8, rejected because a rule lives in `requirements/` and an assignment is a delta; and defining a significant finding as a count of participants, rejected because the severity is what the finding already carries and the count would make the triage arithmetic.
- **Where it lands:** [The Results And Findings](../../requirements/usability-testing-requirements.md#the-results-and-findings), [The Triage](../../requirements/usability-testing-requirements.md#the-triage), and [Assignment 8 Parts 3 to 6](../../assignments/assignment-8.md#part-3-write-the-results).

## A8-DEC-011: One New Requirements File And One New Guide

- **Status:** Accepted
- **Decision:** `requirements/configuration-management-requirements.md` owns the configuration plan, the items, the connections, the evaluation, the recommendation, the public review, and the full example, and it links the course's configuration rules rather than restating them.
  `guides/configuration-management.md` owns the method: the baseline, the inventory, the fields, the connections, the goals, the judgement, the tradeoffs, the first change, the sanitized publication, and the handoff.
  The planning and deployment guides point at it where they touch the configuration, and the tooling page names no new required tool.
- **Why:** one artifact group needs one owner, and the review's method is long enough to be a guide rather than a section of the requirements; a second requirements file would put the same rule in two places.
  The method lives in a guide because it explains how to judge and the requirements say what the artifacts must contain.
- **Alternatives considered:** putting the method in the requirements file, rejected because a rule and a method fail differently and a guide may explain without obliging; a section per group in the requirements file, rejected because the groups are a way to find the items and the rules are the same for all five; and a new tool, rejected because the team already has the checks and the configuration it is judging.
- **Where it lands:** [Configuration Management Requirements](../../requirements/configuration-management-requirements.md), [Guide: Configuration Management](../../guides/configuration-management.md), [Plan The Repository's Upkeep](../../guides/planning-and-tracking.md#plan-the-repositorys-upkeep), and [Step 1](../../guides/deployment-and-environments.md#step-1-map-the-four-environments).

- **Why:** the deck is the taught week, and a syllabus line describing a lecture that was not given sends a reader to a document that does not exist; rebuilding the deck to match an old line would teach a different course.
  The two comments are metadata rather than content, so correcting them changes no slide and no byte of the PDF.

## A8-DEC-014: The Week 8 Report

- **Status:** Accepted
- **Decision:** the Week 8 report carries the results and the configuration in two sections: `## Usability test` as Assignment 7's plan designed it, and `## Configuration management` immediately after it, with the configuration plan's link, the evaluation's link, the baseline, the `Active` item count, the local goals, the first change and its tradeoff, and what is kept.

  The report carries a `## Week 9 handoff` section, and it embeds at most two sanitized screenshots, each in the section that describes it.

- **Alternatives considered:** a row for the plan and a row for the evaluation, rejected because the section links both and the report would then index the same two files twice; a single combined section, rejected because the results and the configuration are different subjects with different evidence; and no screenshot budget, rejected because a report illustrated from the repository is a report that stopped linking.

## A8-DEC-016: The Plan Is Updated In The Same Pull Request

- **Status:** Accepted
- **Decision:** the configuration plan is updated in the same pull request when a change alters what it records, and its `**Reviewed:**` date advances when the plan is reviewed.
  A settings change that leaves the plan accurate needs no update, and a settings change that alters the plan is recorded in the pull request that closes the task.
- **Why:** a plan that describes last month's repository is worse than none, because it is believed and an agent reads it first; a per-change update rule is what keeps the inventory true, and it is the same rule the team's `AGENTS.md` already follows.
  Requiring an update for every settings change would fight a pull request that changes nothing the plan records.
- **Alternatives considered:** updating the plan once a sprint, rejected because an agent reads it between the change and the update; and requiring the plan update only at the release, rejected because the release is after the pull requests that change the configuration.
- **Where it lands:** [Where The Configuration Plan And The Review Live](../../requirements/configuration-management-requirements.md#where-the-configuration-plan-and-the-review-live), [Agent Instructions Requirements](../../requirements/agent-instructions-requirements.md), and [Step 8](../../guides/configuration-management.md#step-8-carry-it-into-week-9).

## A8-DEC-017: The Evaluation Is Goal-First

- **Status:** Accepted
- **Decision:** the team chooses the local goals and explains each in its own words; a local goal is a purpose an artifact set serves, not the project's goal.
  Each goal section carries `**Today:**` the artifacts that achieve it, `**A more convenient way:**` the proposed set with `Keep`, `Merge`, `Replace`, `Cut`, or `Add`, `**Why:**` the goal is still achieved and the change removes a named mechanism, and `**Tradeoffs:**` what the change gives up and why the gain is worth the loss.
  The tradeoff is required, and a change whose tradeoff is worse than the gain is not made.
  The evaluation has no change table, no per-item verdict, no cost table, and no graph paragraph, and `## The First Change` names the one change the team would make first.
- **Why:** the artifacts are the means and the goal is the end, so a goal that four files serve badly is the finding, and a replacement is judged by whether the goal survives rather than by whether the artifact was good.
  A review that only reports missing items pushes a team to add configuration; the course wants a team that can take configuration away when the cost says so, and the tradeoff is what makes the removal honest.
- **Alternatives considered:** an item-by-item verdict with a keep or change per `CFG-nn`, rejected because it judges the artifact and produces no tradeoff; a cost table with a score per item, rejected because the numbers would be invented; and an overall paragraph above the goal sections, rejected because the first change is the headline and the goal sections are the detail.
- **Where it lands:** [The Evaluation](../../requirements/configuration-management-requirements.md#the-evaluation), [Assignment 8 Part 8](../../assignments/assignment-8.md#part-8-write-the-goal-based-configuration-evaluation), and [Steps 4 to 6](../../guides/configuration-management.md#step-4-write-the-local-goals).

## A8-DEC-018: The Configuration Plan Is Simplified

- **Status:** Accepted
- **Decision:** the configuration plan carries one `**Reviewed:**` line, the item fields, the five groups, at least 8 `Active` items, the connections field only, and a dropped item in place.
  It carries no `**Baseline:**`, no `**Properties:**`, no `**Version:**`, no connections table, and no `## Dropped Items` section.
  The plan is kept readable as the repository grows, and the evaluation treats the plan itself as a configuration item when its length becomes a cost.
- **Why:** the plan is a file a reader or an agent opens to find the configuration, and every extra field is a second copy of something the repository or the evaluation already says; a plan that grows faster than the repository becomes the third thing the team has to maintain.
  The evaluation judging the plan is what keeps the plan itself in scope, so simplification is proposed like any other change.
- **Alternatives considered:** a field per item for its version and its properties, rejected because nothing reads them and both are restated from the repository; and a connections table under the items, rejected because the item's own field is where the edge is read.
- **Where it lands:** [The Configuration Items](../../requirements/configuration-management-requirements.md#the-configuration-items), [The Connections](../../requirements/configuration-management-requirements.md#the-connections), and [What Good Looks Like](../../assignments/assignment-8.md#what-good-looks-like).
