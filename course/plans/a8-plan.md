## Design Decisions

The `UT-01` sessions run at the dates the team schedules, from the Week 7 class week to the Week 8 deadline; Week 8 writes the results and reviews the configuration; the results claim what the sessions found, the fixes are planned and triaged, and the configuration review is full-depth with the evaluation as the deliverable; no separate plan and no implementation are required in Week 8, and the recommendation's ordered items are the Week 9 backlog.

- **The week.**
  Week 8 has two streams: the run week of `UT-01`, and the configuration review.
  The run week is the design Assignment 7's plan already wrote: the at-least-three counted sessions, the sanitized session notes, `results.md`, the findings, the triage, the `QR/QRT` verdict, the threshold outcome, `REL-08`, the Sprint Review, the retrospective, and the AI usage report.
  The configuration review is the new stream: the map and the evaluation; the evaluation carries the Keep, Add, Cut, And Simplify recommendation.
  Week 9 prepares the deck, schedules the evaluation's ordered recommendation as task issues, and finalizes the repository; no implementation is required in Week 8.
  The split is what lets the week run the test in the days the results need and still review the configuration without a second sprint.
- **The review's scope.**
  The review judges the whole repository configuration: the delivery configuration and the context an agent reads.
  The five groups are source control and release, checks, environments and secrets, dependencies and builds, and agent context and artifacts.
  The criteria are the course's own configuration rules: the branch protection, the link check, the pinned actions, CI, the environments, the secrets, the contributing guide, the `AGENTS.md`, the identifiers, the links, and the weekly report, indexed with their links in the new requirements file's criteria table.
  An application endpoint is product behaviour, so a defect in it is a risk or a task issue, not a configuration item.
  The course materials are an upstream item the team installs and wires in, and it judges them but does not edit them; the review's improvement is in the team's own repository, such as a shorter `AGENTS.md`, a repository map that points at the skill's router, or one workflow instead of four.
  A review that judges only the product code would miss the configuration the agent actually reads; a review that judges only the agent context would miss the checks and the delivery that make the product trustworthy.
- **The map.**
  `docs/configuration-management.md` is maintained documentation, and it is the configuration's inventory: what the items are, what each is for, which properties matter, what each reads and what reads it, and where it lives.
  It carries at least 12 `Active` `CFG-nn` items in the five groups, one section per item at `### CFG-01`, headed by the identifier alone, with `**Status:**` `Active` or `Dropped`, `**Purpose:**`, `**Properties:**`, `**Connections:**`, `**Where:**`, and a `**Dropped:**` date and reason when an item is removed; a dropped item moves under the map's `## Dropped Items`, so the live inventory stays short and no identifier is reused.
  It carries a connections table, `| From | To | Kind | What breaks |`, where the kind is `reads`, `enforces`, `produces`, `triggers`, or `cites`, and the table is the canonical record of each edge, its kind, and what breaks; each item's `**Connections:**` field names the edges the item is part of, as a reading aid.
  It carries `**Baseline:**`, the release or tag it currently describes, and `**Reviewed:**`, the date it was last reviewed; a baseline is the identified, frozen state of the configuration at a point in time, the map's baseline advances when a release is cut, and the map is updated in the same pull request when the change alters what it records; a settings change that leaves the map accurate needs no update, and a settings change that alters the map is recorded in the pull request that closes the task, because a map that describes last month's repository is worse than none: it is believed.
  The map is the maintained artifact a reader or an agent opens to find the configuration; the evaluation is the judgement of it at one point, and it is not maintained.
- **The evaluation.**
  `reports/week-08/cm-evaluation.md` is the week's judgement of the map.
  It carries `**Baseline:**`, the tag or commit it judged, and `**Reviewed:**`, the date; both are frozen for the evaluation, so a later week can tell what state the verdicts describe and how it differs from the map's current baseline.
  It carries the method, a verdict for each `Active` item, a `Missing` entry for each configuration the repository needs and does not have, the cost of each judged item, the strengths to keep, the problems, at least two traced paths, its own `## Keep, Add, Cut, And Simplify` section, the not-planned list, and the evidence; the requirements file fixes the section headings, the verdict table, the cost table's columns and units, the evidence kinds, and the not-planned table, so the example can be checked.
  The verdict is `Adequate`, `Weak`, `Missing`, `Too heavy`, or `Not judged`: adequate is an item that does its job at a cost the team can carry, weak is an item whose property fails or whose connection is missing in a way that matters, too heavy is an item that works but costs more than it returns for the team, not judged is an item the team could not assess, and missing is a configuration the repository needs and does not have, named in words and judged `Missing`.
  The cost is stated, not implied: the maintenance time, the review surface, the tokens an agent spends when it reads the item, and what fails when the item drifts; a figure the team cannot measure is an estimate or `not measured` with the reason.
  A problem that endangers a `TOS-nn`, a `QR-nn`, or a `RISK-nn` cites it, so a `Weak` item tied to `QR-02` is different from a `Weak` item that is housekeeping; an item with no tie is recorded as upkeep, which the configuration-management requirements define as repository work that keeps the artifacts buildable, checkable, and deliverable and traces to no `TOS-nn`, `QR-nn`, or `RISK-nn`, and its reason says what breaks if it drifts.
  The evaluation is a judgement, so an `Adequate` verdict needs its evidence as much as a failing one does.
- **The cost and the too-heavy test.**
  The `Too heavy` verdict is the week's distinctive judgement: an item whose cost exceeds the value it returns.
  The cost model is the maintenance time, the number of files or steps a change touches, the tokens an agent spends to read it, and the failure cost when it drifts.
  The test is the team's size and the remaining course: a team of the course's size with two sprints left cannot carry a second telemetry backend, a fourth dashboard, a custom release script, or an `AGENTS.md` longer than the repository it describes.
  The evaluation states whether the configuration is right-sized and supports the statement with its cost table; no verdict count is prescribed, and a `Too heavy` verdict is used where the cost exceeds the value rather than to fill a quota.
  The distinction matters because a review that only reports missing items pushes a team to add configuration; the course wants the team to be able to take configuration away when the cost says so, and a team that finds the configuration right-sized says why.
- **The recommendation.**
  `reports/week-08/cm-evaluation.md` is the week's judgement, and its `## Keep, Add, Cut, And Simplify` section is the recommendation.
  It says what the team would keep as it is, what it would add, what it would remove or merge, and what it would simplify, each bucket with its items or a sentence saying why it is empty, each item with the `CFG-nn` it keeps, cuts, or simplifies or, for an addition, the configuration's name in words because it has no `CFG-nn` yet, the change, the reason, and the `TOS-nn`, `QR-nn`, or `RISK-nn` it serves or its upkeep.

  It carries a not-planned list: the changes the team considered and dropped, with the reason, so the recommendation reads as a design rather than a wish list.

## Edge Cases And Failure Modes

- **The team uses no coding agent.**
  The agent-context group is still reviewed: the map, the docs, the identifiers, the links, the `AGENTS.md`, and the skill's installation are configuration, and a team that does not install the skill records the decision and judges the router it does use; the course does not require an agent.
- **The course materials are read-only.**
  The review judges them as an upstream item and judges the team's wiring of them; an improvement is a shorter `AGENTS.md`, a repository map that points at the router, or a smaller set of instructions, never an edit to the submodule.
- **The review exposes a secret or an address.**
  The public file carries no value and no address, the deployment address stays in the Moodle wrapper per the existing rows, and a leaked credential is revoked or rotated and reported per the incident response.
- **The map grows longer than the repository.**
  A dropped item moves under `## Dropped Items` and a merged item is recorded once, so the live inventory shrinks; the evaluation treats the map itself as a configuration item and may recommend merging or shortening it.
- **The review would change too much.**
  The evaluation's recommendation is scoped, the not-planned list records what it does not do, a `Missing` item the team does not plan is in it, and no change is forced.
- **An optional change is enacted.**
  It is a task issue, a pull request, the map update in that pull request, the green checks, and the release when it is product-visible; it is extra evidence, not a requirement.
- **A session does not count.**
  The A7 rule holds: the raw text and the recording are removed, the code is retired, a replacement is recruited under the next code, and the report says how many counted sessions there were.
- **Fewer than three sessions run.**
  The `QR/QRT` row stays `Not verified` or moves to `SPRINT-09` with a reason, the results claim no result, and the configuration review still runs; the report declares the shortfall.
- **The results are late and the configuration review is on time.**
  The report carries the configuration section and the results section with the open session window declared, and the Week 9 plan carries the results when they land.
- **The recommendation changes after the results.**
  The review records the decision as a `DEC-nnn`, the evaluation's recommendation changes, and the report says what changed.
- **The team cannot judge a configuration item.**
  The verdict is `Not judged`; the evaluation records the reason, the risk it carries, and its not-planned disposition, so every item is accounted for.
- **The Week 9 handoff slips.**
  The map is the maintained artifact, the evaluation is the Week 8 judgement, the results are the deck's evidence, the private data stays until grading, and the Week 9 plan owns the deck and the final state.
