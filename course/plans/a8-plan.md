## Design Decisions

The `UT-01` sessions run at the dates the team schedules, from the Week 7 class week to the Week 8 deadline; Week 8 writes the results and reviews the configuration; the results claim what the sessions found, the fixes are planned and triaged, and the configuration review is full-depth with the evaluation as the deliverable; no separate plan and no implementation are required in Week 8, and the evaluation schedules no work.

- **The week.**
  Week 8 has two streams: the run week of `UT-01`, and the configuration review.
  The run week is the design Assignment 7's plan already wrote: the at-least-three counted sessions, the sanitized session notes, `results.md`, the findings, the triage, the `QR/QRT` verdict, the threshold outcome, `REL-08`, the Sprint Review, the retrospective, and the AI usage report.
  The configuration review is the new stream: the configuration plan and the goal-based evaluation; the evaluation carries the local goals, the first change, and the tradeoffs.
  Week 9 prepares the deck, finalizes the repository from its own plan, and reflects; the evaluation schedules no work, and no implementation is required in Week 8.
  The split is what lets the week run the test in the days the results need and still review the configuration without a second sprint.
- **The review's scope.**
  The review judges the whole repository configuration: the delivery configuration and the context an agent reads.
  The five groups are source control and release, checks, environments and secrets, dependencies and builds, and agent context and artifacts.
  The criteria are the course's own configuration rules, linked from each item's `**What good looks like:**`: the branch protection, the pull request and review rules, and the release and changelog rules for source control and release; the link check, the pinned actions, and continuous integration for the checks; the environments and the deployment runbook, the secrets rule and `.env.example`, and the incident response for environments and secrets; dependency pinning and Dependabot, the reproducible build, and the large-file rule for dependencies and builds; and the contributing guide, the team's `AGENTS.md` and the skill's `SKILL.md`, the identifier rules, the links, the maintained documentation's locations and indexes, and the weekly-report rules for the agent context and the artifacts.
  An application endpoint is product behaviour, so a defect in it is a risk or a task issue, not a configuration item.
  The course materials are an upstream item the team installs and wires in, and it judges them but does not edit them; the review's improvement is in the team's own repository, such as a shorter `AGENTS.md`, a repository map that points at the skill's router, or one workflow instead of four.
  A review that judges only the product code would miss the configuration the agent actually reads; a review that judges only the agent context would miss the checks and the delivery that make the product trustworthy.
- **The configuration plan.**
  `docs/configuration-plan.md` is maintained documentation, and it is the configuration's inventory: what the items are, what each is for, how each is identified and owned, what each reads and what reads it, and where it lives.
  A configuration item is a maintained file, setting, or process the project depends on to be built, checked, delivered, or understood, including the maintained documentation in `docs/`, the entry points an agent reads, and the process that produces the weekly report; a particular week's report is an instance, not an item; a set of files is one item at its index or entry point, such as the functional requirements index or the architecture `README.md`.
  It carries `**Reviewed:**`, the date it was last reviewed, and at least 8 `Active` `CFG-nn` items in the five groups, with at least one in each group.
  It is one section per item at `### CFG-01`, headed by the identifier alone, with the first line naming the item, and the item's fields are `**Status:**` `Active` or `Dropped`, `**Type:**` a short phrase saying what kind of thing it is, such as `document`, `workflow`, `CI pipeline`, `setting`, `dependency`, `skill`, or `process`, `**Purpose:**` a short paragraph saying what it is for and what breaks without it, `**Owner:**` the person or role responsible for keeping it true, `**Where:**` the file path or the settings page in words, `**Connections:**` its incident edges with their kind and what breaks, `**What good looks like:**` a short paragraph stating the target the item must meet and linking the rule it must meet, and `**Dropped:**` the date and reason when it is removed.
  A dropped item stays where it is with `**Status:**` `Dropped` and its `**Dropped:**` date and reason, so no identifier is reused and the reader sees the history in place; the `Active` count excludes it.
  The item records no version and no baseline: the repository's history and the evaluation's `**Baseline:**` identify the state, so a per-item version or a document-level baseline would only repeat them.
  The plan has no connections table: each item's `**Connections:**` field is the single record of its edges, their kind, and what breaks, so there is one place to maintain.
  The configuration plan is updated in the same pull request when the change alters what it records; a settings change that leaves the configuration plan accurate needs no update; a settings change that alters the configuration plan is recorded in the pull request that closes the task, because a configuration plan that describes last month's repository is worse than none: it is believed; and its `**Reviewed:**` date advances when the plan is reviewed.
  The configuration plan is the maintained artifact a reader or an agent opens to find the configuration; the evaluation is the week's goal-based change proposal on it, and it is not maintained.
- **The evaluation.**
  `reports/week-08/cm-evaluation.md` is the week's qualitative opinion, organized by the local goals the artifacts serve, not by the items.
  It carries `**Baseline:**`, the tag or commit it judged, and `**Reviewed:**`, the date; both are frozen, so a later week can tell what state the goals describe and how it differs from the plan's current state.
  It carries one `## Method` paragraph, one `##` section per local goal, one `## What We Could Not Judge` note, and one `## The First Change` paragraph; the requirements file fixes the headings, the goal section's labels, the `Keep`, `Merge`, `Replace`, `Cut`, and `Add` changes, and the evidence kinds, so the example can be checked.
  The team chooses the local goals and explains each in its own words; a local goal is a purpose an artifact set serves, such as deciding what the product should be, specifying what it must do, verifying it, planning and tracking it, learning from its users, communicating it, or keeping the context trustworthy for a reader or an agent; it is not the project's goal, and the lecture's final quiz on the purpose of TOS, VP, ADR, FR, RISK, US, and DEC is the warm-up.
  Each goal section carries `**Today:**`, the artifacts that achieve the goal now, linked to the plan's `CFG-nn` sections and named in words when an artifact is not in the plan; `**A more convenient way:**`, the proposed set and the concrete change, using `Keep`, `Merge`, `Replace`, `Cut`, or `Add`; `**Why:**`, the goal is still achieved and the change removes duplication, a manual step, a readerless file, staleness, an unverifiable check, a context cost, or another mechanism, with the evidence from the team's own use; and `**Tradeoffs:**`, what the more convenient way gives up, such as traceability, customer visibility, one source of truth, the agent's context, the review surface, or a learning step, and why the gain is worth the loss or why the team would not make the change.
  The tradeoff is not optional: a replacement that hides its loss is the review the course does not want; a team that finds the change not worth its tradeoff records that and keeps the artifact.
  The evaluation does not judge whether an item meets its `**What good looks like:**`, because the criteria are mandatory and an item that does not conform is fixed, not debated; it judges whether the set of artifacts is the most convenient way to achieve the goal.
  A change never removes an item the criteria require: a required item is fixed or simplified, and only configuration beyond the criteria is cut.
  An item the team could not judge is the `What We Could Not Judge` note with the reason and the risk it carries; a `Missing` configuration is named in words and proposed in a goal section, and gets a `CFG-nn` only once it exists.
  The goal sections say what the team would keep, merge, replace, cut, or add; an artifact no goal section proposes to change stays as it is, so there is no separate keep list.
  No maintenance, review-surface, token, or failure cost is measured, no count is prescribed, and an item that costs more than its job is `Simplify`, `Merge`, `Replace`, or `Cut` with the mechanism and the tradeoff named, not a cost estimate.
- **The goal test.**
  The opinion is goal-based because the team can say what an artifact set is for and what a more convenient way costs, and a number invented to fill a cell is worse than a sentence a reader can check.
  The test is the team's size and the remaining course: a team of the course's size with this sprint and one more cannot carry a third telemetry backend, a fifth dashboard, a custom release script, or an `AGENTS.md` longer than the repository it describes.
  The goal is the unit because the artifacts are the means: a goal that four files serve badly is the finding, and the replacement is judged by whether the goal survives, not by whether the artifact was good.
  The evaluation has no separate overall paragraph: `## The First Change` carries the headline, and the goal sections carry the detail.
  The distinction matters because a review that only reports missing items pushes a team to add configuration; the course wants the team to be able to take configuration away when the cost says so, and a team that finds the configuration right-sized says why in its goal sections.
- **The changes.**
  `reports/week-08/cm-evaluation.md` is the week's opinion, and its goal sections are its changes: what the team would keep, merge, replace, cut, or add to achieve each local goal, with the tradeoffs.
  The goal sections are not an ordered backlog: the `## The First Change` paragraph names the one change the team would make first, and the evaluation schedules none of the changes into `SPRINT-09`.
  No separate plan is required: the goal sections and the first change are the evaluation's conclusion, not a second document, and no task issue follows from them.
- **No separate plan and no implementation.**

  A team that enacts a change does so before the code freeze; the evaluation schedules none, and an enactment is extra evidence rather than a planned item.

1. **Set the review baseline and read the rules.**
   The `REL-07` tag or the commit the review starts from, the date, the course's configuration rules the plan's `**What good looks like:**` links, and the configuration plan's update rule.

## Edge Cases And Failure Modes

- **The team uses no coding agent.**
  The agent-context group is still reviewed: the configuration plan, the docs, the identifiers, the links, the `AGENTS.md`, and the skill's installation are configuration, and a team that does not install the skill records the decision and judges the router it does use; the course does not require an agent.
- **The course materials are read-only.**
  The review judges them as an upstream item and judges the team's wiring of them; an improvement is a shorter `AGENTS.md`, a repository map that points at the router, or a smaller set of instructions, never an edit to the submodule.
- **The review exposes a secret or an address.**
  The public file carries no value and no address, the deployment address stays in the Moodle wrapper per the existing rows, and a leaked credential is revoked or rotated and reported per the incident response.
- **The configuration plan grows longer than the repository.**
  A dropped item stays in place with `**Status:**` `Dropped`, so the live inventory is readable, and the evaluation treats the configuration plan itself as a configuration item and may propose shortening or merging it in a goal section, with the tradeoff named.
- **The review would change too much.**
  The evaluation's goal sections are scoped, the `What We Could Not Judge` note records what it does not judge, the first change is the one the team would make first, and no change is forced.
- **An optional change is enacted.**
  It is a task issue, a pull request, the configuration plan update in that pull request when the change alters what it records, the green checks, and the release when it is product-visible; it is extra evidence, not a requirement.
- **A session does not count.**
  The A7 rule holds: the raw text and the recording are removed, the code is retired, a replacement is recruited under the next code, and the report says how many counted sessions there were.
- **Fewer than three sessions run.**
  The `QR/QRT` row stays `Not verified` or moves to `SPRINT-09` with a reason, `results.md` carries the qualitative record with no aggregate statistic, the results claim no result, and the configuration review still runs; the report declares the shortfall.
- **The results are late and the configuration review is on time.**
  The report carries the configuration section and the results section with the open session window declared, and the Week 9 plan carries the results when they land.
- **The evaluation changes after the results.**
  The review records the decision as a `DEC-nnn`, the evaluation's goal sections and first change change, and the report says what changed.
- **The team cannot judge an item.**
  The evaluation's `What We Could Not Judge` note records the reason and the risk it carries, so the item is accounted for without one.
- **A goal has no artifact today.**
  The goal section's `**Today:**` says so, and the `**A more convenient way:**` is an `Add` named in words; the new artifact gets a `CFG-nn` only once it exists.
- **A replacement loses the goal.**
  The `**Tradeoffs:**` line says so, and the team either keeps the artifact or chooses a replacement that keeps the goal; a change that loses the goal is not a more convenient way.
- **The Week 9 handoff slips.**
  The configuration plan is the maintained artifact, the evaluation is the Week 8 judgement, the results are the deck's evidence, the private data stays until grading, and the Week 9 plan owns the deck and the final state.
