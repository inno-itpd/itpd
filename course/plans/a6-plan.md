## Design Decisions

Week 6 is the product analytics and the observability, the product is instrumented for both, the data is visible in two dashboards, the quality signals are defined as `SLI`s, and one observability requirement is implemented and tested.
The week then prepares the threshold review, and the deck is not part of it.

- **Scope.**
  Assignment 6 is the whole week outside the deck: `docs/analytics.md` and its metric tree, the event table and the instrumentation, the analytics backend and its dashboard, `docs/observability.md` and its `SLI`s, the OpenObserve backend and its `SLI` dashboard, the two functional requirements and the two stories, the two ADRs and the container view, the observability requirement and its test, the optional runtime re-run that cites an `SLI`, the threshold review, `REL-06`, the Sprint Review, the retrospective, and the AI usage report.
  Logs, traces, and alerts are not required: the lecture teaches them, and the week grades the metrics, the `SLI`s, and the two dashboards.
  Week 6 has no pitch deck, and it runs no experiment.
- **The analytics plan.**
  `docs/analytics.md` is one maintained page: the value moment, the north star, the counter-metric, the L1 and L2 inputs, the metric tree, the event table, the pipeline, the dashboard, what the events collect and where the data lives, and the full example.
  Its metrics are `##` sections with the metric in the heading, not an identifier family, cited as `docs/analytics.md#<metric-anchor>`, as a feature is cited.
- **The metric tree.**
  The plan carries one north star, one counter-metric, one L1 input, and one or two L2 inputs that feed the L1; the tree is one table that links each metric and says what it feeds.
  The north star satisfies the seven criteria of the North Star Framework: it expresses value, it represents the vision and strategy, it is a leading indicator, it is actionable, it is understandable, it is measurable, and it is not a vanity metric ([the Open Practice Library](https://openpracticelibrary.com/practice/north-star-framework/)); the plan names at least one rejected vanity metric, such as GitHub stars, with the reason.
  A rate states its numerator and denominator; a count states its unit and window.
- **The events.**
  The event table is one table with `Event`, `Fires when`, `Fields`, `Metrics fed`, and `Collected at`; `Metrics fed` is plural because one event can feed several metrics, and each metric's section lists the events that feed it; `Collected at` names the product container and the environment that emit the event.
  One naming convention applies to every event; no event carries personal data, as the visibility requirements define it; an event identifies a user by an opaque identifier when it needs to.
  The table covers the core task end to end, so Week 7's usability work has the events it needs.
- **The analytics pipeline.**
  The product emits the events through its instrumentation, the analytics backend stores them, and the dashboard serves the charts from the backend.
  The recommended backend is OpenPanel, because it is open source and self-hosts on the team's VM or a campus machine; the dashboard is reachable from the university network only, and a team that chooses another self-hosted backend documents it.
  Staging and production are separate projects or environments, so a dry run in staging never pollutes the production metric, and no event leaves the campus network; the analytics plan records the separation.
  `docs/deployment.md` owns the pipeline and its steps, the configuration and secrets are installed outside the repository, and `.env.example` carries the shape.
- **The analytics dashboard.**

## Edge Cases And Failure Modes

- **The VM is not available this week:** OpenObserve runs on another machine on the campus network; if none is available, the observability work waits, the report declares it, and the observability requirement's test stays `Not verified` with `Planned for sprint: SPRINT-06`, so the week's required demonstration is missing and the goal is not claimed; the analytics work still runs, and the test moves with the pipeline.
- **The VM is too small for both backends:** OpenObserve runs on a second campus machine, the address stays private-only, no telemetry leaves the campus network, the deviation is declared in the report, and the dashboard's evidence is a sanitized screenshot.
- **The analytics host is not available or not reachable:** The team self-hosts OpenPanel or uses another documented backend on a campus machine, keeps the two environments separate, sends no personal data, and declares the deviation.
- **A dashboard is not reachable from the university network:** The team checks the access before the Sprint Review; when the customer cannot reach it, the meeting shows the sanitized screenshots and the deployment evidence, and the report records why.
- **The `SLI` has no data:** The runtime `QRT` fails or stays `Not verified`, the row keeps its result and evidence, the report records the measured value or the absence, and the release claims no quality through it.
- **The runtime `QRT` has no suitable signal:** The re-run is optional, so the team skips it and the observability requirement's short-window test remains the week's demonstration; a team that re-runs and fails records the result and still has the demonstration.
- **A longer test's window is still open at the deadline:** The row stays `Not verified` with its `Planned for sprint`, `Checked` is `None`, and the report declares the open window; the test's verdict is recorded in the next sprint.
- **An event would carry personal data:** The field is dropped or replaced with an opaque identifier; an event with a free-text field is not instrumented, and the metric is recomputed from the anonymous events.
- **A metric has no event:** The event is added in the same pull request, or the metric is dropped; no number is invented and no chart is drawn from a spreadsheet the team keeps outside the pipeline.
- **A team already has a dashboard:** It is kept, the new chart is added to it, and the plan records where it runs; no second backend is required.
- **A team has no runtime quality requirement:** The observability requirement still gives the week a `QRT` and an `SLI`, and its short-window test is the required demonstration; the optional re-run is skipped, and the team does not invent a quality requirement to carry the `SLI`.
- **A team has no analytics events yet:** The core task's events are instrumented first, and the metric tree is limited to what the events feed; a metric the events cannot feed is dropped.
- **The threshold has no analytics-measured goal:** Nothing is forced; the team records the current measures and the proposal, and the customer may leave the threshold unchanged.
- **The threshold goal is missed:** It is set `Missed` with its `**Outcome:**` and the evidence, which is a finding rather than a failure, and the report says what changed.
- **A public file would name a dashboard:** It does not: the addresses and credentials are Moodle-only, the plans and the tests use environment variables or placeholders, the screenshots are sanitized, and no link is excluded from the link check.
- **A user-facing analytics capability is added:** It needs a story, a functional requirement, and a feature entry, per the existing rules; the assignment does not require one.
- **A team draws a pipeline diagram anyway:** It is the team's choice, no rule asks for it, and the deployment table and the container view stay the records.
- **A team wants to run an experiment:** It does not; the week sets up the metrics and records the focus metric for a future operated system, and the report says the north star is not yet measurable.
